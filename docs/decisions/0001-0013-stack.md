# Stack Decision — 2D Fighting Game (MK2-style, rollback netplay)

> **Status:** Accepted — foundational
> **Date:** 2026-08-22
> **Supersedes:** generic recommendations in `BLUEPRINT.md` §11
> **Commit as:** `docs/decisions/0001-through-0012-stack.md`, or split per-ADR

---

## The one-paragraph version

A 2D fighter with rollback netcode is a **deterministic fixed-point simulation
with a rendering layer bolted on top**. Nearly every stack decision follows
from that single sentence. We take a thin platform layer (SDL3), write the
simulation ourselves in fixed-point integer math at a fixed 60Hz, keep all
game state in one flat memcpy-able POD struct, and hand that struct to a
rollback library (GekkoNet). We deliberately reject the two things a generic
2D game would reach for first — an ECS and a physics engine — because both
actively obstruct rollback.

## ADR 0001 — Language: orthodox C++

**Decision.** C++ restricted to a documented subset.

**Use:** RAII, references, `constexpr`, namespaces, `enum class`, operator
overloading (fixed-point math types only), templates for containers only,
plain structs.

**Forbid:** exceptions (`-fno-exceptions`), RTTI (`-fno-rtti`), inheritance
beyond one level, template metaprogramming, `iostreams`, `shared_ptr` as a
default, `std::string` in the sim, STL containers in the sim.

**Rationale.** RAII and sanitizers remove the memory-bug class that agent-written
C is prone to. The subset restriction exists because agents silently pick
different C++ dialects across sessions; an unrestricted codebase becomes
stylistically incoherent, and incoherent diffs are slow to review — and review
is the project's binding constraint.

**Enforcement.** Reviewer checklist item: *does this diff use a language
feature outside ADR 0001?*

---

## ADR 0002 — Determinism: mandatory, fixed-point

**Decision.** The simulation is bit-identical across platforms. Fixed-point
integer math throughout. No floats below the sim boundary, ever.

**Requirements:**
- `Fixed` type: `int32_t`, 16 fractional bits. Documented overflow behavior.
- Fixed 60Hz timestep. **No `dt` in the simulation.** All durations are integer
  frame counts.
- Seeded RNG, part of `GameState`, deterministic algorithm (PCG32 or xorshift).
  Never `rand()`.
- No wall-clock reads in sim.
- No iteration over unordered containers in sim.
- Input is data: a per-frame bitfield, not polled engine state.

**Rationale.** Rollback requires re-simulating past frames and arriving at
identical results. Cross-platform float divergence is the classic failure mode
that ships broken and is nearly impossible to debug after the fact. Fixed-point
makes it structurally impossible.

**Consequences.** No standard trig in sim — use lookup tables in `src/sim/math/`.
Fixed jump arcs (which matches MK2's design anyway). Rendering may use floats;
the boundary is explicit and one-way.

## ADR 0003 — Platform layer: SDL3

**Decision.** SDL3 for window, input, gamepad, and audio device.

**Rationale.** Fighting games are latency-sensitive as a competitive property;
SDL3 gives direct control over event polling and main-loop timing where
higher-level libraries impose a per-frame model. SDL3 is also extremely well
represented in training data, so agents produce correct SDL3 code rather than
guessing — which matters when agents write a meaningful share of the codebase.

**Rejected:** raylib (main loop too opinionated for rollback; input model too
coarse). A raylib throwaway prototype to validate feel is acceptable and
explicitly out of scope for this architecture.

---

## ADR 0004 — Rendering: SDL3 GPU API

**Decision.** SDL3's GPU API. Fall back to SDL_Renderer if it becomes a
time sink — the game is textured quads and this is not where the difficulty
lies.

**Rationale.** Rendering is genuinely not the hard part of a fighter. Sprites,
a background, a UI layer. Any competent 2D path suffices; do not spend
engineering budget here.

**Rendering reads `GameState` and never writes it.** Interpolation between
sim frames happens in the render layer only.

---

## ADR 0005 — Entity model: no ECS

**Decision.** All game state in one flat, trivially-copyable POD struct.

```cpp
struct GameState {
    Fighter    fighters[2];
    Projectile projectiles[MAX_PROJECTILES];
    int32_t    frame;
    int32_t    round_timer;
    int32_t    round_number;
    RngState   rng;
};
static_assert(std::is_trivially_copyable_v<GameState>);
static_assert(sizeof(GameState) < 4096);
```

**Rules:** no pointers (use indices), no heap allocation, no `std::` containers,
fixed-size arrays only.

**Rationale.** Rollback saves and restores full state up to 8× per frame. A
memcpy of a small POD struct is effectively free; an ECS registry snapshot is
not. We also have ~10 entities, not thousands — an ECS solves a problem this
game does not have.

**Reverses** the generic ECS recommendation in `BLUEPRINT.md` §11. That advice
assumed entity-soup and no rollback.

---

## ADR 0006 — Physics: none

**Decision.** Custom collision. Three box types, AABB overlap only.

- **Hurtbox** — where a fighter can be hit
- **Hitbox** — where a fighter hits
- **Pushbox** — body collision, prevents overlap

Movement is bespoke: constant gravity, **fixed jump arcs committed at takeoff**
(matches MK2), integer velocities.

**Rationale.** Fighting games do not use physics engines. A solver would fight
the frame-data model, introduce float nondeterminism, and add a large
dependency to replace ~100 lines of testable code.

---

## ADR 0007 — Netcode: GekkoNet

**Decision.** GekkoNet for rollback. BSD-2, CMake-native, actively maintained.

**Rationale.** Native C++ rather than an FFI wrapper over a Rust library.
Non-callback control flow, which is materially easier to unit test than GGPO's
callback model. GGPO is the well-documented ancestor and remains the fallback;
its maintenance status is the concern.

**Integration contract.** GekkoNet needs exactly three things, all of which
ADRs 0002 and 0005 already give us:
1. `save_state()` → memcpy `GameState`
2. `load_state()` → memcpy back
3. `advance_frame(inputs)` → pure function, no side effects

**Sequencing.** Build local versus first. The sim is architected for rollback
from day one, but netplay integration is deferred until two characters play
well offline. Do not build netcode before the game is fun.

**This is the most replaceable decision in this document.** The real decision
is ADRs 0002 and 0005 — deterministic fixed-point sim, flat POD state, pure
`advance_frame`. Any GGPO-lineage library (GekkoNet, GGPO, GGRS via FFI, or
a hand-rolled implementation) consumes that same three-function contract.
If GekkoNet proves unsuitable, swapping it is a days-scale change confined to
one integration file. Getting 0002 or 0005 wrong is a rewrite.

Treat the netcode library as an implementation detail behind an interface;
treat determinism as architecture.

---

## ADR 0008 — Transport: deferred behind an interface

**Decision.** Define a minimal transport interface now. Use GekkoNet's built-in
UDP/ASIO for LAN and development. Defer internet P2P.

**Rationale.** Rollback and transport are separate problems. P2P over the
internet needs NAT traversal — hole punching or a relay. Valve's
GameNetworkingSockets provides this via Steam relay if we ship on Steam, and
that decision depends on distribution plans we haven't made.

---

## ADR 0009 — Data format: TOML

**Decision.** All frame data, character definitions, and move properties in
TOML via tomlplusplus. Hot-reloadable in debug builds.

```toml
[moves.uppercut]
input       = "d,df,f+HP"
startup     = 5
active      = 3
recovery    = 24
damage      = 12
hitstun     = 21
blockstun   = 14
cancel_into = ["special", "super"]

[[moves.uppercut.hitboxes]]
frames = [6, 8]
x = 20; y = -40; w = 32; h = 48
```

**Rationale.** This is the highest-leverage architectural decision in the
project. Frame data as text is diffable, reviewable, agent-editable, testable,
and changeable without a rebuild. It moves the bulk of game content out of
code and into a form the whole workflow handles well.

**Balance changes are data commits, not code commits.**

---

## ADR 0010 — Build: CMake + CPM.cmake

**Decision.** CMake with CPM.cmake for dependencies. Migrate to vcpkg past ~10
dependencies.

**Compile-time budget — treat as a hard requirement:**
- Full rebuild: **under 60s**
- Incremental: **under 5s**

If exceeded, fix it before adding features. The agent feedback loop degrades
sharply past this, and `BLUEPRINT.md` §1 depends on a fast honest signal.

**Presets:** `debug` (ASan + UBSan), `release`, `profile` (Tracy enabled).

---

## ADR 0011 — Testing: doctest + replay + desync

**Decision.** doctest, chosen for compile speed over Catch2/GoogleTest.

**Four tiers:**

| Tier | Covers | Target |
|---|---|---|
| Unit | Fixed-point math, input parser, hitbox overlap, damage scaling, move state machine | <1s |
| Replay | Recorded inputs + seed → final state hash | <10s |
| Desync | **Same replay across OS matrix → identical per-frame hashes** | CI only |
| Smoke | Headless boot, 600 ticks, no crash | <5s |

**The desync test is the most important test in the project.** CI matrix across
Linux, Windows, and macOS runners, asserting bit-identical state hashes. Cross-
platform divergence is the failure that ships broken and cannot be debugged
after release. Catch it on the commit that introduces it.

**Replay library.** Maintain 50+ recordings covering combos, edge cases, round
transitions, and every past bug. When a balance change legitimately breaks a
replay, re-record **in the same commit** as the change — never in a separate
"fix tests" commit, which destroys the signal.

## ADR 0012 — Support libraries

| Library | Purpose | Note |
|---|---|---|
| Dear ImGui | Hitbox viewer, frame data inspector, state debugger | Build this in week one |
| miniaudio | Audio playback | Single header; **render layer only, never sim** |
| Tracy | Frame profiling | Profile preset only |
| tomlplusplus | Frame data parsing | Load-time only, never in sim loop |

**Audio and VFX live entirely in the render layer.** They must not be part of
`GameState` and must not be rolled back — restoring particle and audio state is
a known rollback pain point and we avoid it structurally by keeping them out.

## Architecture boundary

The single most important line in the codebase:

```
┌────────────────────────────────────────────────┐
│  src/sim/    DETERMINISTIC                     │
│  fixed-point only · no float · no allocation   │
│  no I/O · no clock · no rand() · POD state     │
│  pure function: (GameState, Inputs) → GameState│
├──────────────── one-way ───────────────────────┤
│  src/render/  src/audio/  src/ui/              │
│  floats, interpolation, effects                │
│  reads GameState · never writes it             │
└────────────────────────────────────────────────┘
```

**Reviewer checklist item:** *does this diff introduce a float, allocation,
clock read, or `std::` container below the sim boundary?* Mechanical to check,
catastrophic if missed.

| Replay recorder/player | Move state machine |

| Training mode overlays | Fixed-point math types |
| Input remapping | |
| Test coverage backfill | |

**The sim is a human-led zone permanently.** Desync is the ultimate
green-but-broken failure — it compiles, tests pass locally, and it breaks only
in real matches between real players on different machines.

## Scope

**Two characters, complete, before anything else.** Full movesets, hitstun,
blockstun, combos, round flow, win conditions — and it must feel right. If two
characters play well, a third is content work. If they don't, twelve won't help.

**Build training mode early.** Hitbox display, frame data readout, input
display, hitstun counter. It is the debugging environment and it doubles as a
shipped feature.

**Build the frame-data editor before authoring content.** Hand-writing hitbox
TOML for even two characters will break you. It is also an ideal agent task:
self-contained tooling, no sim contact.

**The editor is a separate build target** (`tools/framedata_editor/`), not part
of the game binary. It links SDL3 + Dear ImGui, loads sprites, and reads and
writes the *same* TOML the sim consumes — that shared schema is the only
coupling between them. Consequences:

- Editor code never ships in the game, and can freely use floats, `std::string`,
  allocation, and anything else ADR 0001 forbids in the sim
- It is fully agent-parallelizable — it cannot desync anything
- Schema changes to the TOML are the one thing that must be coordinated;
  treat `docs/framedata_schema.md` as the contract and version it

A third target, `tools/replay_inspector/`, follows the same pattern and is
worth building once the replay suite grows.

**IP note.** Mortal Kombat is Warner Bros. property. Building a clone to learn
is fine; distributing anything using MK characters, names, or assets is not.
Original characters in the MK2 *style* keeps this clean — the fighting engine
is identical either way.

## ADR 0013 — Art pipeline: boxes first, 3D-to-sprites later

**Decision.** v1 renders fighters as colored rectangles. When real art is
needed, the pipeline is Blender → locked orthographic camera → sprite sheets.

**Rationale.** Feel in a fighting game is entirely frame data — startup,
active, recovery, hitstun. Colored rectangles feel identical to finished
sprites. Tuning the game to fun with zero art means we will know exactly which
frames are required rather than guessing, and committing to an art pipeline
before the engine works is the most common way a solo fighting game dies.

3D-to-sprites is chosen over hand-drawn pixel art and digitized actors because
rig reuse makes character two cheap, iteration is a re-render rather than a
redraw (critical while frame data is still moving), and lighting and camera
consistency are free.

**Consequences.**
- The renderer must treat sprites as swappable from day one: it draws from a
  sprite manifest, and the placeholder path is one manifest implementation.
  No rendering code assumes rectangles.
- The sprite packer and Blender export script are separate tooling targets
  (see `tools/`), fully agent-parallelizable, and cannot desync anything.
- Sprite dimensions are deliberately undecided until v2 — 3D rendering makes
  this a late decision rather than an early one.

**This is not a placeholder decision.** Do not propose replacing boxes with
art before the v1 definition of done in `DESIGN.md` §6 is met.

## Scope tier — MEDIUM

Per `BLUEPRINT.md` § *Scaling This to Your Project*.

**Setup budget: 1–2 days.** Phase 0 + Phase 1 combined. If it runs longer,
something has grown that shouldn't have — cut it.

**Small tier is not available for this project.** A rollback fighter requires
determinism, replay tests, and CI as structural prerequisites, not optional
rigor. The sim architecture *is* the scaffolding.

### Three Large-tier exceptions — all forced by rollback

1. **Desync CI matrix** — Linux/Windows/macOS runners, per-frame state hash
   comparison. This alone is why the project isn't plain Medium.
2. **Full replay test library** — target 50+ recordings. Medium tier treats
   replay as optional; for a fighter it is the primary regression net.
3. **Versioned frame-data schema doc** — `docs/framedata_schema.md`, because
   the editor is a separate build target sharing a contract with the sim.

### Explicitly cut from Medium — do not build these

- **No separate `OWNERSHIP.md`.** The sim/render boundary in `ARCHITECTURE.md`
  is already the ownership map, and this is a solo project. A second file
  restating it is ceremony.
- **No CI perf gates yet.** Tracy in the profile preset suffices until there
  is a game to profile.
- **No integration branch workflow.** That is for 3+ concurrent branches. At
  2 agents, merge sequentially to `main`.

### Agent ceiling: 2

Tools only (frame-data editor, sprite packer, replay inspector, menus, audio).
The sim is human-led permanently — see the parallelism map above.

## The rule that holds the whole thing together

**If it affects the outcome of a match, it is in `GameState` and it is
deterministic. If it does not, it is in the render layer and it never touches
the sim.**

Every ambiguous decision in this project resolves against that sentence.
